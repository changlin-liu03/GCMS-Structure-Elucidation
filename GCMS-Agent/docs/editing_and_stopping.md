# 编辑验收与停止条件

[English](editing_and_stopping.en.md) | **简体中文**

本文首先描述默认 `case_batch` 流程。配置默认值和覆盖关系见[配置说明](../configs/README.md)；旧 `legacy` 模式的差异在文末单独说明。

## 试验与正式提交

模型收到当前探索图及其 `graph_version`，它可能与历史最佳图不同。每个候选有独立的原子 ID、图版本和状态。

一次 `analyze_proposals` 调用对每个候选最多接受三个替代方案；一个会话可以多次调用，次数由 `max_trial_batches` 等会话额度约束。每个候选最终在 `submit_reviews` 中最多引用三个试验。单个方案中的基本编辑操作项数没有固定上限。这些限制不能合并理解成“整个会话只能试三个方案”。

分析参数包含 `candidate_id`、`base_version`、`operations`，版本须匹配当前候选。正式提交的方案引用只包含 `trial_id`、`reason`、`peak_refs`、`operation_explanations`，宿主从当前会话试验记录恢复操作并核验；不重复提交原始操作。

```text
核对版本 → 在图副本上执行整组编辑 → 严格化学及往返检查
        → 固定规则枚举 → 点分计算 → 生成试验 ID
        → 正式引用提交 → 宿主复核与去重 → 选择新探索状态
```

同批试验基于对应候选的当前快照，试验本身不改变候选图。每条基本操作须有非空说明，峰引用须来自观测谱；字段通过检查不表示程序已经证明说明中的机理。具体结构契约见 [batch_server.py](../src/gcms_agent/tools/batch_server.py)。

## 验收与历史最佳

宿主依次检查组成、化学合法性、已见结构和证据状态，见[验收函数](../src/gcms_agent/scoring/acceptance.py)与[批审工作流](../src/gcms_agent/workflow/case.py)。

- 首次合法修复：旧图不满足最终约束，新图通过后可保存为合法版本，不要求正分。若证据计算失败，仍以 `tool_error` 结束且不生成正常分数，不能把“合法”当作“证据完整”。
- 合法图探索：不同、未见且通过约束的新结构，证据枚举完整后可以成为下一轮起点；允许同分或降分，不再要求新增支持峰或固定分差。
- 多个方案获准时：优先选择有分数的方案，按点分降序、兼容下界降序、canonical SMILES 升序选择一个提交；当前下界等于点分。被拒绝的方案与原图记录仍保留。

[最佳状态管理](../src/gcms_agent/workflow/search_state.py)独立保存正式接受过的合法结构。完整评分优先，其次取最高点分，完全同分保留较早结构。结束时输出最佳状态，同时另存探索游标供允许的恢复使用；未提交试验不会自动成为最佳输出。

## 完整审阅与停滞

`review_complete` 由宿主判断，需要合法 `keep`、无本轮编辑提案、四项检查完成，以及不同合法结构的完整证据试验或可核验历史探索；还须不存在提升历史最佳分数却未提交的合格试验。

四项检查为 `graph_read`、`valence_checked`、`spectrum_checked`、`alternatives_checked`。历史探索必须与当前图、谱图及规则绑定核验，模型口头声称已经探索不算依据。

没有接受新结构且有完整探索依据时，批审增加停滞计数；接受新结构后清零，探索不足时也清零。零试验、仅非法试验或只重复当前结构会得到 `exploration_insufficient` 反馈，仍受轮数和时间上限约束。`stop_review` 仅兼容旧提示，不满足宿主条件的停止请求会被忽略。

## 停止状态

| 原因 | 含义 |
|---|---|
| `objective_ceiling` | 合法结构的覆盖分达到 1（采用代码中的数值容差），不代表唯一身份确认 |
| `review_complete` | 满足批审协议及探索验收条件 |
| `stagnation` | 达到连续停滞轮数，默认 2 轮 |
| `max_rounds` | 达到候选轮数，默认 3 轮 |
| `timeout` | 候选或请求时间限制触发；候选累计默认 900 秒 |
| `format_retry_exhausted` | 格式修复额度耗尽 |
| `turn_limit`、`output_limit` | 会话资源结束，未获得足够的正式提交 |
| `budget_exhausted`、`case_budget_exhausted` | 显式设置的金额限制触发 |
| `case_session_limit`、`case_transport_failure_limit` | 同谱有效会话额度或已豁免连接失败上限触发 |
| `offpeak_wait` | 当前时段不允许启动新会话，需之后显式恢复 |
| `tool_error`、服务/认证/计费错误 | 执行失败，保存可用状态与相应诊断 |

停止条件由[候选终止函数](../src/gcms_agent/workflow/termination.py)、工作流及会话控制共同实施。候选结构状态与停止原因分别记录，例如 `corrected` 与 `max_rounds` 可以同时出现。化学非法结构的 `final_smiles` 为 `null`；合法但资源未完成的结果可保留结构，同时标注排名未完成。

已验证提交之后发生输出或轮次错误，仅在最终用量已知且符合客户端恢复条件时可保留提交；服务错误不会被资源标记覆盖。网络失败和格式错误不应冒充完成一轮化学探索。

## 会话与金额限制

默认 economy 每会话最多 6 个 SDK turn，其中预留 1 个用于提交，最多 4 次分析调用；查询、提交及控制逻辑可能使实际分析次数低于上限。同一谱图最多并行两批，每谱默认有效会话额度为 8。不同计数的含义见[配置说明](../configs/README.md)。

当前总金额与单谱金额默认不设上限；设置 `--budget-cny` 或相应配置后才启用对应限制。费用预留只是调度估算，未知用量保留估算，不等于服务商硬账单上限。`max_output_tokens: null` 使用 CLI/服务默认额度，并非无限输出。`offpeak_only` 使高峰时停止新会话并保存进度，不会定时后台续跑。

## 检查点与恢复

[运行器](../src/gcms_agent/workflow/runner.py)要求恢复时输入哈希、运行模式、后端、科学配置及源码/技能/资源指纹兼容。检查点保存图版本、探索历史、最佳状态和回执；费用结算及请求标识用于避免重放重复记账。不要通过改清单或删除版本检查强行接续不兼容结果。

总运行预算和输入 token 预留估算有显式调整通道：输入预留只允许不变或提高；已有总预算只允许按运行器支持的方式提高，原本无限额的运行不能在恢复时改为有限额。单谱上限及其他科学配置仍参加配置一致性检查。这些例外不适用于任意配置修改。

源码指纹覆盖 `src/`、`skills/`、`resources/`、`configs/` 中的文本文件，说明或注释变化也可能改变指纹。新的科学配置应使用新运行目录。

## 旧模式与基线

`legacy` 每个候选使用独立审阅流程，没有默认批审的四项检查和共享探索验收；其停滞计数在没有接受方案时增加。不能把批审的 `review_complete` 条件套用到旧模式。实现见 [candidate.py](../src/gcms_agent/workflow/candidate.py)。

`baseline` 不运行模型编辑，以 `baseline_only` 保存确定性结果。候选化学失败与模型未完成是不同状态；各类指标的口径见[评分与评估](scoring.md#evaluation)。
